# UI, reliability, scaling, and security review

Reviewed base: `5c41fe3d9d9e9be82c55c47ac85b59a8135a6211` (main), 24 October 2026.

## Changes made

| Area | Confirmed problem | Change |
| --- | --- | --- |
| Desktop header | Many equally prominent actions; conflicting 64px code and 74px stylesheet minimum; cramped smaller windows | Consistent header height, simpler shapes, frequent actions visible, secondary actions in a keyboard-accessible More menu; additional actions move into the menu below 1200px |
| Header resizing | Brand breakpoint at 1050px was skipped by the responsive-mode cache | Include brand breakpoint in the cache key |
| Web access — high | All interfaces exposed live feeds, archives, alerts, PTZ, recording changes, and deletion without authentication | Random 256-bit per-launch access link, fragment exchanged for an HttpOnly/SameSite cookie; protect every data/control route; remove remote deletion |
| Web commands — high | State changes allowed through GET; cross-site requests could trigger commands | GET becomes read-only; commands require JSON and reject foreign Origin headers |
| Web rendering — high | Camera names, alert details, filenames and identifiers interpolated into HTML and inline JavaScript | Escape dynamic template values, JSON-encode handler arguments, encode URL identifiers, restrict media URLs to local paths |
| Recording downloads — high | Filename validation missed Windows drive-relative paths and NTFS alternate streams | Reject colons and non-MP4 names; resolve paths and enforce containment within recording folders |
| HTTP resource use — medium | Unbounded connection threads and body reads; malformed numeric values could interrupt request handling | Maximum 32 concurrent handlers, 10-second socket timeout, 16 KiB JSON limit, finite bounded numeric parsing |
| Video seeking | Video responses advertised ranges but always returned whole files | Shared MP4 response helper implements bounded, open-ended and suffix byte ranges; invalid ranges return 416 |
| Private media caching | Surveillance media had public cache headers | Private/no-store responses |
| Viewer stability | Three-second camera polling recreated every MJPEG element | Preserve image elements while refreshing status, name, metrics and recording state |
| Web tile actions | Solo displayed the first camera rather than the selected camera; close immediately fetched the camera back | Respect selected camera and track hidden feeds; camera-tree selection restores a hidden feed |
| Misleading web controls | Hardcoded signal strength and simulated success messages | Remove fake signal strength; quality changes actual JPEG quality/FPS; unsupported audio/retention controls direct users to desktop |
| Recording RAM | Fixed 60-frame queue could retain about 1.39 GiB of 3840×2160 BGR pixels per recorder | Expected-frame queue budget approximately 32 MiB; one 4K frame fits, five 1080p frames fit. This limits queue capacity, not total process memory |
| JPEG CPU use | Concurrent viewers could encode the same frame simultaneously; cache ignored requested quality | Serialize viewer encoding with a separate lock and include quality in cache checks; capture/display do not acquire that lock |
| Configuration integrity | Direct writes could truncate the saved configuration on failure | Write/fsync a temporary file and atomically replace the destination; preserve old file if replacement fails |
| Camera identity | Count-based generated IDs could collide after a camera was deleted | UUID-based IDs |
| Headless mode | Stale WebStreamingServer constructor caused immediate startup failure; motion signal used an incompatible slot and nonexistent dispatcher method | Use the current server interface and AlertManager notification path; apply alert settings and flush history at shutdown |

## Validation

- `python -m unittest discover -s tests -v`: **16 tests passed**. These use local HTTP requests, temporary configuration/video fixtures, and simulated workers. They do not connect to cameras.
- Browser smoke test in Chromium 151: access-link exchange, fragment removal, literal rendering of malicious camera/alert strings, inline handler arguments with hostile IDs, recording toggles, stable stream element identity across polling, solo/close behavior, and header/workspace fit at 390/768/1280px passed.
- PyQt6 offscreen smoke test: header capsules remain separate and inside the window at 960, 1020, 1100, 1280 and 1920px; More actions invoke their original controls. Previews were inspected visually.
- YOLOv5 model loaded successfully through OpenCV; inference on a synthetic blank frame returned no detections.
- Python compilation and `git diff --check` passed.
- Tested on Windows, Python 3.12.14, PyQt6 6.11.0/Qt 6.11.2, OpenCV 5.0.0.93, NumPy 2.5.4, psutil 7.2.2, Pillow 13.0.0, qrcode 8.2.
- pip-audit reported no known advisories for those installed application packages and their Qt/sip/colorama dependencies. It reported advisories for the disposable environment's older pip 25.0.1; pip is tooling rather than an application dependency. This does not audit every version permitted by the existing lower-bound requirements or bundled native libraries.

## Access changes

Open **More → Mobile access** and copy/scan the complete local link. It contains `/#access=...`; treat it like a password. The browser removes the fragment after exchanging it for a session cookie. Restarting the server invalidates old links and browser sessions. Headless mode prints its private access link to its local console. Protect access to that console/log.

For another hostname, such as a VPN address or HTTPS tunnel, open that hostname and paste the access code when prompted. A proxy must preserve the original Host header for same-origin command checks. A trusted HTTPS Origin causes the session cookie to be marked Secure.

Direct API clients must exchange the access token with `POST /api/session` using `application/json` and retain the returned cookie. Control requests must use JSON POST. Remote camera deletion is no longer supported; use the desktop app.

## Remaining work and limits

1. **Transport and identity:** the embedded server still uses HTTP and a single shared access capability with operator permissions. Use a trusted LAN/VPN or an HTTPS reverse proxy for remote access. Internet-scale operation needs user accounts/roles, revocation, per-client limits and a production server architecture. Connection caps mitigate resource growth but do not make the service immune to denial of service.
2. **Stored credentials:** camera passwords, RTSP credentials and notification secrets remain in local configuration. `.gitignore` excludes the active configuration, but local secrets should move to Windows Credential Manager/DPAPI with a migration path. Historical commits and release binaries were not exhaustively scanned for secrets.
3. **Large camera fleets:** each stream still has its own decoder, AI model/executor and frame buffers. Shared/batched inference, substream policies, hardware decode measurements and bounded alert/notification work queues are the next scaling priorities. The recorder queue budget does not include ring buffers, encoder buffers, AI tensors or copies held elsewhere.
4. **Dependencies/releases:** requirements remain lower bounds, and native OpenCV/Qt/FFmpeg contents are outside the Python advisory check. Pin a tested release environment, review binary provenance and add Windows CI plus dependency/security scanning before shipping an installer.
5. **Hardware and endurance:** no physical camera, two-way audio, ONVIF PTZ device, live RTSP reconnect, disk-full workload, notification delivery, installer, or multi-day recording soak test was available. Real throughput and maximum camera/viewer counts have not been established.

This is a source review with targeted regression tests, not a complete penetration test or a certification that the application has no vulnerabilities.
